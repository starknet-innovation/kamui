# Runtime secret delivery through AWS Secrets Manager — design

**Status: implemented and tested offline; not applied to any account.** Run order is at the end.

Today `08-prepare-runtime.sh` writes each host's runtime files into private local files on the
operator's machine, and nothing gets them onto the hosts. The services refuse to start without
them. This design moves them into AWS Secrets Manager and has each host fetch its own at start.

## What each host needs

All files land under `/etc/kamui`. Owner and mode come from `runtime.py`'s `ownership()` and must
match exactly, because compose mounts them as Docker secrets read by a specific container user.

| Host | File | Owner | Mode | Source |
|---|---|---|---|---|
| backend | `secrets/POSTGRES_PASSWORD`, `secrets/APP_DATABASE_PASSWORD` | 999 | 0400 | generated by 08 |
| backend | `backup/pgbackrest.conf` | 999 | 0400 | generated by 08 |
| backend | `secrets/DATABASE_URL`, `funding-policy.json` | 1000 | 0400 | generated by 08 |
| backend | `secrets/OPERATOR_DATABASE_URL` | 0 | 0400 | generated by 08 |
| backend | `backend.public.env`, `keychain.public.env`, `watcher.public.env`, `backup/operator.settings` | 0 | 0600 | generated by 08 |
| backend | `secrets/RELAYER_PRIVATE_KEY` | 1000 | 0400 | **operator only** |
| pepper | `pepper.private.env` | 0 | 0600 | generated by 08 |

## Proposed design

### 1. Storage

Per account, one customer-managed KMS key used only for these secrets, and:

| Secret | Holds | Who writes the value |
|---|---|---|
| `kamui-sepolia/backend/runtime` | a JSON bundle of every generated backend file above, with its path, owner, mode and SHA-256 | the new operator script `12` |
| `kamui-sepolia/backend/relayer-private-key` | the relayer signing key | **the operator, by hand.** No Kamui tooling reads, writes or logs this value. |
| `kamui-sepolia/pepper/runtime` | `pepper.private.env` as a bundle | script `12` |

Each secret has a resource policy allowing `GetSecretValue` only to that host's role, and denying
it to every GitHub Actions role. The KMS key policy allows `kms:Decrypt` only to that host role,
and only when the call comes through Secrets Manager (`kms:ViaService`).

### 2. Writing — a new operator step

`13-store-runtime-secrets.sh`, run on the workstation after `08`:

- validates the runtime manifest from `08` (existing `runtime.validate`);
- builds each host's bundle and calls `PutSecretValue`;
- records the returned version id and the bundle's SHA-256 privately, so a lost response is
  reconciled by version rather than resent blind (same discipline as the other numbered steps);
- **never calls `GetSecretValue`**. Values go through one dedicated wrapper method, which logs only
  the secret's ARN, the request token and the value's SHA-256, and passes the real request through
  a temporary private file deleted as soon as the call returns. The generic request path can call
  neither `GetSecretValue` nor `PutSecretValue`; only `DescribeSecret` is an allowed read;
- reuses a token derived from the bundle's hash, so a lost response is resent safely instead of
  creating a second version;
- reports whether the relayer secret still holds only its CloudFormation placeholder, from version
  metadata alone.

The relayer key is put in by the operator directly, for example:

```sh
aws secretsmanager put-secret-value --secret-id kamui-sepolia/backend/relayer-private-key \
  --secret-string file:///path/to/private/relayer-key --profile kamui-backend-test
```

### 3. Reading — on the host, at every start

A new root-run oneshot unit, `kamui-secrets@<role>.service`, shipped in the host package:

- fetches this host's secrets with the instance role;
- writes each file atomically into `/etc/kamui` with the exact owner and mode, and refuses any
  path outside the expected set;
- verifies every file against the SHA-256 in the bundle;
- never prints a value; its log lines carry only file names, the secret version id and status.

`kamui@<role>.service` gains `Requires=` and `After=` on it, so the stack never starts without
current files. **Rotation** becomes: put a new secret version, then restart the unit.

### 4. Container isolation from the instance role — required

The host role can then read the relayer key, and today every container can reach the instance
metadata service (the launch template's hop limit of 2 lets bridge-networked containers through).
So an internet-facing container — Caddy, the keychain — could fetch the relayer key with the
host's credentials. The current README already flags this as an open review item. This design
closes it:

- compose gives each network a fixed subnet;
- a new host unit, applied before Docker starts its containers, adds `DOCKER-USER` iptables rules
  that drop traffic to `169.254.169.254` from every container network **except**
  `backup_egress` (backend: pgBackRest to S3) and `kms_egress` (pepper: KMS MAC);
- an acceptance check proves it: an IMDS request from inside the keychain and Caddy containers
  must fail, and from the backup and pepper containers must succeed.

The host-level fetch in step 3 runs as root on the host, not in a container, so it is unaffected.

### 5. IAM changes

The existing host roles carry deliberate explicit KMS denies (`NoOtherKmsResource` in pepper, a
deny-all in backend). An explicit deny also blocks the decryption Secrets Manager performs with
the caller's permissions, so **these denies must be narrowed** — a deny cannot be overridden by an
added allow. The proposed change to `setup/identity-storage.json`, per host role:

- allow `secretsmanager:GetSecretValue` on exactly that host's secret ARNs;
- carve one exception out of the KMS deny: `kms:Decrypt` on the new runtime-secrets key only,
  with `kms:ViaService = secretsmanager.eu-west-1.amazonaws.com`;
- keep every other KMS deny as it is. The pepper role still cannot use or change any key except
  the MAC operations on the pepper key, plus this one decrypt path.

Because CI's guardrail denies `cloudformation:*`, this stays an operator-run stack update, which
keeps host IAM out of CI's reach.

The original `setup/identity-storage.json` is not edited: earlier setup steps record its hash and
verify the stacks they created against it. The successor is `setup/identity-secrets.json`, and a
test proves it equals the original except for the added resources and outputs and the two narrowed
denies. `12-add-host-secrets.sh` applies it through a CloudFormation change set:

- the first run creates the change set, checks it and stops, changing nothing;
- the check refuses anything but the expected additions and an in-place update of the host role,
  any replacement, a stack whose deployed template has drifted, and a change set that differs from
  the one reviewed;
- only `--execute` applies it. Reruns are idempotent, and `06-addresses` keeps verifying the
  updated stacks.

## Decisions

1. **Secrets Manager vs a private S3 object.** An S3 object with SSE-S3 encryption needs no KMS,
   so it would avoid narrowing the identity stack's denies. Secrets Manager is the standard place
   for secrets, gives versioning and per-secret policies, and is what you asked for.
   *Recommendation: Secrets Manager.*
2. **Where the new resources live.** Either in the identity CloudFormation stack, or in
   Terraform. The CI apply role may call `secretsmanager:DeleteSecret` and change secret
   containers, so putting the relayer secret in Terraform would put it within CI's reach.
   *Recommendation: the identity CloudFormation stack, operator-run.*
3. **Fetch on every start vs once at install.** *Recommendation: every start*, so rotation is a
   restart and a host never runs on stale files.

## What it takes to ship

- identity template and setup tooling: a reviewed update path, then one operator-run stack update
  per account;
- host package: the fetch unit and script, the IMDS firewall unit, fixed compose subnets, and
  `kamui@.service` ordering — a new release through `11`, then `07` to `10`;
- workstation: script `12`, the narrowed AWS-wrapper allowlist, tests;
- acceptance: files present with exact owners and modes, IMDS blocked from the internet-facing
  containers, and no secret value in any log.

This is Sepolia only. Mainnet needs its own review of custody, rotation and the instance-role
credential boundary.

## Run order

From `infra/aws/lean/setup` in a clean checkout of `main`:

1. `./12-add-host-secrets.sh` — creates and checks the change sets, and prints each change. Read
   them. Nothing has changed yet.
2. `./12-add-host-secrets.sh --execute` — applies them: the KMS key, the secrets, and the host role
   update, in both accounts.
3. `./13-store-runtime-secrets.sh` — stores each host's files. It reports the relayer key as a
   placeholder until step 4.
4. Put the relayer key into `kamui-sepolia/backend/relayer-private-key` yourself, from a private
   file, with the backend profile. Rerun 13 to see it reported as stored.
5. `./11-supersede-unstarted-release.sh`, then `07` to `10` — ships the host package with the fetch
   unit, the metadata-service firewall and the fixed subnets.

At the next stack start, each host fetches its files and fences its containers before anything runs.
